Most work is not greenfield. The constraints are that someone else has to read the
diff, the code around it already made choices, and the cheapest correct change is
almost always the smallest one that fully solves the problem.

## Non-negotiable

1. **Search for an existing implementation before writing new code.** If you write new
   code anyway, say what you found and why it did not fit.
   *Why:* a duplicated helper is two things to fix when the behaviour is wrong, and the
   second copy is the one nobody remembers to update.
   *Check:* a graph or symbol search for the operation, the domain noun, and the likely
   verb — not just the exact name you would have chosen.

2. **Every public function, method, and type carries a doc comment** stating: what it
   does, what each parameter *means* and what values are valid, what it returns, how it
   fails, and **where and why it is called**.
   *Why:* the signature gives types; it does not give meaning, valid ranges, ownership,
   units, thread-safety, or which of three similar functions to call. The call-site
   context is what a reader cannot reconstruct without reading every caller.
   *Check:* the language's native doc format — XML docs, docstring, rustdoc, JSDoc,
   doc comment — so tooling and IDEs pick it up.

3. **Make the smallest change that fully solves the problem.** Diff size is a cost paid
   by every reviewer.
   *Why:* a large diff hides the two lines that matter, and the risk of a change scales
   with what it touches, not with how good the new code is.
   *Exception:* a smaller diff that leaves a correctness, safety, or measured
   performance problem in place is not the smaller change — it is a deferred one.

4. **Refactoring is allowed within the change's own context, and only there.** Same
   module, namespace, or package; something you are already modifying; something whose
   callers you can enumerate.
   *Why:* inside that boundary you can see every caller and verify the change. Outside
   it you are altering a contract for code you have not read.

5. **Outside that context, ask before changing a shared function.** Offer both options:
   a new function alongside it, or a refactor of the original — with the trade-off
   stated.
   *Why:* the right answer depends on how many callers exist and whether they want the
   new behaviour, and that is the caller's decision, not yours.
   *Check:* the question names the callers you found and what each would need.

6. **Detected codebase conventions override this repo's stylistic preferences.**
   Correctness, safety, and security rules never yield.
   *Why:* a change that reads as foreign is a change reviewers cannot evaluate quickly,
   and consistency inside one codebase is worth more than any individual style
   preference. But no convention makes a race condition acceptable.
   *Check:* `.agent/conventions.md`, generated by `python tools/detect_conventions.py`.

## Prefer

7. **Extend or parameterize an existing function over duplicating it** — when the
   abstraction is honest. If the parameter is a boolean that selects between two
   unrelated behaviours, write the second function instead.

8. **Change behaviour at the narrowest scope that works**: the call site, then the
   function, then the module, then the interface. Each step outward multiplies the
   blast radius.

9. **Separate refactoring commits from behaviour commits.** A diff that moves code *and*
   changes it cannot be reviewed, because the reviewer cannot tell which lines are which.

10. **Follow the local idiom even when you would write it differently** — naming, error
    handling, layering, test structure, comment density. Consistency is a property of
    the codebase, not of the file.

11. **Read the callers before changing a signature.** Enumerate them; if you cannot
    enumerate them, the function is public API and rule 5 applies.

12. **Leave a note rather than a fix** when you find an unrelated problem: an issue, a
    `TODO` with context, or a line in the report. Fixing it silently enlarges the diff
    and buries your actual change.

13. **In a genuinely new context — a new service, module, or package with no established
    convention — use the best approach available** rather than importing habits from an
    unrelated part of the repo. Say which conventions you set, so the next person
    inherits a decision rather than an accident.

## Avoid

14. **Copy-paste with a small tweak.** Either the difference is a parameter, or the two
    things are genuinely different and should not share a shape.

15. **Rewriting working code to your preferred style.** It is unreviewable, it destroys
    blame history, and it is not what was asked.

16. **Speculative generality** — an interface with one implementation, a parameter no
    caller passes, an abstraction for a second case that does not exist yet.

17. **Renaming or reformatting files you are otherwise not changing.** It buries the
    real diff.

18. **Changing a public signature without a deprecation path**, when callers are outside
    your control.

19. **Comments that narrate the code.** `// increment i` is noise. Inline comments state
    constraints the code cannot express — see the split in rule 2.

20. **Assuming the surrounding code is wrong because it is unfamiliar.** Find out why it
    is that way first; the reason is often in the git history or a linked issue.
